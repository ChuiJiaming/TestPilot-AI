Status: active reconciliation register. V10.3 remains the requirements baseline; the OpenAPI and SQL are candidate artifacts.

## M04 — generation jobs

- Runtime candidate routes now include project-scoped generation history, GET-by-ID, cancel, retry, and proposal acceptance. `/projects/{id}/generations` is canonical per V10.3 chapter 42; the older project-scoped `/projects/{id}/test-cases/generate` route now shares the same handler and is explicitly deprecated in runtime and OpenAPI. New history/read operations remain additive candidates and need unified contract validation.
- The UI now reloads generation history with keyset pagination and reloads ordered suite-case associations. Suite/plan editing and removal semantics are not implemented because their write contract was not defined.
- Candidate migration 009 and repository code add durable generation job, proposal acceptance, usage metrics, worker leases, and Outbox intent. The migration is unapplied. An OpenAI-compatible LangChain adapter, Celery task, and leased Outbox publisher exist. The API key and per-model price map must be configured in the Worker environment; no worker or provider call has been run.
- Owner decisions (2026-10-27): first provider is an OpenAI-compatible API; provider retries are capped at three automatic generation retries with exponential backoff; every proposal is tagged `UNCLASSIFIED` and requires human review. The LangChain adapter requires a configured API key and explicit per-model input/output rates; no provider call has been made. Generation worker leases use a 15-second Beat recovery task; expired attempt tokens are invalidated before retry, the same three-retry cap covers provider failures and lease expiry, and exhausted or canceled jobs end visibly. Delays use the existing Outbox exponential schedule (2, 4, 8 seconds). A manual retry does not reset the job's automatic retry counter. Generated proposals use the owner-approved strict DSL v2 validator before draft-version persistence; all proposals remain non-runnable until explicit review/publish.
- Runtime configuration contract: set `TESTPILOT_DATABASE_URL`, `TESTPILOT_CELERY_BROKER_URL` (or reuse `TESTPILOT_REDIS_URL`), `TESTPILOT_LLM_API_KEY`, optional HTTPS `TESTPILOT_LLM_BASE_URL`, and `TESTPILOT_LLM_PRICING_JSON` keyed by the exact model name with `input_usd_per_million` and `output_usd_per_million`. No credentials or price values are checked into the repository. Run the worker with `celery -A apps.api.app.cases.worker:celery_app worker --loglevel=INFO`; run its Outbox Beat dispatcher separately with `celery -A apps.api.app.cases.worker:celery_app beat --loglevel=INFO`. These commands are implementation guidance only and have not been executed.

## M05 — case DSL and version review

- Owner decision (2026-10-28): retain strict DSL v2 as the TestPilot project contract. This deliberately differs from V10.3 §44.2, which specifies DSL v3 and `contracts/test_case_v103.schema.json`; implementation must not claim V10.3 DSL conformance. Any future move to v3 requires a separate owner decision and migration/compatibility plan. The v2 validator accepts `navigate(url)`, `click(locator)`, `fill(locator,text)`, the documented locator set, and text/url assertions; unknown fields and types are rejected.
- `POST /projects/{id}/test-cases` now marks `title` required, and `POST /test-cases/{id}/versions` marks `dsl` required; suite creation similarly marks `name` required. These candidate DTO corrections match current persistence needs but still require contract validation. Other optional/nullability and response-shape differences may remain.
- New and rollback-created immutable versions enter `PENDING_APPROVAL` and create their `case_version` Approval row plus `approval.requested` audit entry in the same transaction. The version author is the requester; only a different project writer can decide. Case-version approvals have no expiry because V10.3 defines none. Only approved versions can be published; rollback creates a new version and never rewrites its source. Historical title/review state remains unknown.
- The generic `POST /approvals/{id}/decide` accepts the V10.3 wire decisions `APPROVE`/`REJECT` and a required reason, then stores `APPROVED`/`REJECTED`. The existing version-number approval route uses its documented decision/reason body; the version-id `/approve` route is bodyless and means approve. Runtime and OpenAPI still need unified HTTP contract validation.
- Owner decision (2026-10-27): publish `name` is the human-readable version title. Runtime stores and returns `version_name`; the web review screen lets the publisher set it. Migration 008 adds the nullable column so historical rows remain explicitly unknown. OpenAPI and frontend contracts are synchronized; validation remains deferred.
- Audit chain source rule: for each organization, lock its `organizations` row, read the prior `entry_hash` by descending audit ID, and SHA-256 the UTF-8 bytes of compact sorted-key JSON (`ensure_ascii=false`) for the version-1 envelope `{organization_id, actor_user_id, action, resource_type, resource_id, metadata, created_at, previous_hash, version}`. UUIDs are canonical strings, timestamps are UTC ISO-8601 with six fractional digits and `Z`, nulls are JSON null, and the digest is lowercase hex. The append participates in the business transaction. This is source-defined only; database immutability and external archive verification remain unvalidated.

## M07–M09 — execution backbone

- Candidate source consumes RUN_REQUESTED, atomically records processed_events with plan admission, dispatches attempt-fenced Run execution, and periodically scans queued Runs and expired leases. Event and poll consumers use the same serial/bounded plan lock. Concurrency has not been tested.
- Candidate Run APIs cover create/read/list, pause/resume/cancel/retry, steps, single-use SSE tickets, and event replay. The Run Console reads snapshots and reconnects with a new ticket. HTTP authorization, cursor expiry, and browser reconnection remain unverified.
- `WAITING_APPROVAL` now creates or reuses a project-scoped Run Approval in the same transaction. `POST /approvals/{id}/decide` rechecks project write access, requester/decider separation, pending state and expiry while locking Run then Approval; decision, Run/step state, chained audit, durable events and resume Outbox intent commit together. The request body preserves V10.3 `APPROVE`/`REJECT` plus required reason. Rejection or expiry marks the Run `FAILED`; approval records explicit manual reconciliation, issues a new attempt token and queues `RUN_RESUME_REQUESTED`. The executor skips the human-adjudicated unsafe action on that new attempt and still evaluates the immutable case assertions. Run approvals expire 30 minutes after creation (`expires_at <= now` is expired); a 60-second Beat sweep processes up to 100 due approvals. These are owner-selected source rules, not verified behavior.
- Candidate M07 execution uses stored DSL versions, deterministic assertions, a LangGraph Postgres checkpointer, and a checkpoint allowlist of Run/RunCase/snapshot IDs, step/retry/budget counters, schema version, completed action ID, and attempt token. Budget-gated structured Planner/Explorer calls now use the configured OpenAI-compatible model and bounded page-control observations; proposals cannot change published action/assertion identities or locators. Model-call allowance is run-wide, transactionally decremented, and preserved across recovery. Model configuration and M07 behavior remain unverified. Recovery, Approval Gate, and Analyzer remain later-phase work.
- Candidate M08 uses a separate non-root Playwright Worker, mTLS Gateway forwarding and Worker registration, scoped expiring worker-affinity job tokens, heartbeat-based discovery, least-loaded assignment, exact FQDN allowlists, DNS-pinned egress proxy using the configured IPv4 resolver, request interception, session limits/TTL, readiness, and a drain route. The Worker Compose candidate sets CPU/memory/PID, read-only/capability, dedicated subnet, IPv6-off, and resolver settings. A host DOCKER-USER ACL script now targets the dedicated Worker subnet and rebuilds its managed chain through `iptables-restore`; it remains unapplied. Certificate provisioning and ACL enforcement remain deployment gates. No Worker image, mTLS flow, browser action, or egress negative case was run.
- Candidate migration 012 adds Run request metadata and event replay floor; migration 013 adds the bounded approval-expiry sweep index. Both are unapplied. SecretRef values remain metadata-only and execution fails closed with SECRET_PROVIDER_UNAVAILABLE when a snapshot carries a SecretRef.
- Phase 3 acceptance is pending unified validation. No tests, migration execution, builds, browser flows, security checks, or deployments were run for these source changes.
