# Phase 2 contract gaps and implementation boundaries

Status: active reconciliation register. V10.3 remains the requirements baseline; the OpenAPI and SQL are candidate artifacts.

## M04 — generation jobs

- Runtime candidate routes now include project-scoped generation history, the prose-compatible `/projects/{id}/test-cases/generate` alias, GET-by-ID, cancel, retry, and proposal acceptance. The two new history/read operations are documented as additive candidates; remaining operationIds and response semantics still need reconciliation against V10.3.
- The UI now reloads generation history with keyset pagination and reloads ordered suite-case associations. Suite/plan editing and removal semantics are not implemented because their write contract was not defined.
- Candidate migration 009 and repository code add durable generation job, proposal acceptance, usage metrics, worker leases, and Outbox intent. The migration is unapplied. An OpenAI-compatible LangChain adapter, Celery task, and leased Outbox publisher exist. The API key and per-model price map must be configured in the Worker environment; no worker or provider call has been run.
- Owner decisions (2026-10-27): first provider is an OpenAI-compatible API; provider retries are capped at three automatic generation retries with exponential backoff; every proposal is tagged `UNCLASSIFIED` and requires human review. The LangChain adapter requires a configured API key and explicit per-model input/output rates; no provider call has been made. Generation worker leases use a 15-second Beat recovery task; expired attempt tokens are invalidated before retry, the same three-retry cap covers provider failures and lease expiry, and exhausted or canceled jobs end visibly. Delays use the existing Outbox exponential schedule (2, 4, 8 seconds). A manual retry does not reset the job's automatic retry counter. Generated proposals use the owner-approved strict DSL v2 validator before draft-version persistence; all proposals remain non-runnable until explicit review/publish.
- Runtime configuration contract: set `TESTPILOT_DATABASE_URL`, `TESTPILOT_CELERY_BROKER_URL` (or reuse `TESTPILOT_REDIS_URL`), `TESTPILOT_LLM_API_KEY`, optional HTTPS `TESTPILOT_LLM_BASE_URL`, and `TESTPILOT_LLM_PRICING_JSON` keyed by the exact model name with `input_usd_per_million` and `output_usd_per_million`. No credentials or price values are checked into the repository. Run the worker with `celery -A apps.api.app.cases.worker:celery_app worker --loglevel=INFO`; run its Outbox Beat dispatcher separately with `celery -A apps.api.app.cases.worker:celery_app beat --loglevel=INFO`. These commands are implementation guidance only and have not been executed.

## M05 — case DSL and version review

- Owner approved and runtime now validates strict DSL v2: `navigate(url)`, `click(locator)`, `fill(locator,text)`; locator `by` is role/label/placeholder/text/test_id/css plus `value`; role locator optionally carries `name` and `exact`; assertions are text(locator,expected,match) or url(expected,match), with exact/contains matching. Unknown fields and unknown action/locator/assertion types are rejected. This DSL is candidate-specific to TestPilot; validate it against V10.3 traceability during the unified contract pass.
- `POST /projects/{id}/test-cases` now marks `title` required, and `POST /test-cases/{id}/versions` marks `dsl` required; suite creation similarly marks `name` required. These candidate DTO corrections match current persistence needs but still require contract validation. Other optional/nullability and response-shape differences may remain.
- The existing approvals table is Run-bound (`run_id NOT NULL`); `test_case_versions` lacks review status, changelog, DSL title and approval metadata; `test_cases` has no published-version pointer. The additive migration `008_case_version_review.sql` proposes those persistence links but is not applied or DB-validated. Legacy versions intentionally keep unknown title/review status rather than being assigned inferred values.
- Runtime aliases for approve and rollback delegate to the same lifecycle implementation; rollback by numeric `target_version` creates a new draft, archive is a soft status change, and Diff takes `against_version_id` and compares two immutable snapshots. These route semantics are represented consistently by the handler and candidate OpenAPI; validation against V10.3 remains deferred.
- Owner decision (2026-10-27): publish `name` is the human-readable version title. Runtime stores and returns `version_name`; the web review screen lets the publisher set it. Migration 008 adds the nullable column so historical rows remain explicitly unknown. OpenAPI and frontend contracts are synchronized; validation remains deferred.
- Approval records use the version author as requester and require a different authenticated reviewer, matching the candidate separation-of-duties extension. Case-version approvals have no expiry because V10.3 defines no expiry policy; existing Run approval expiry remains unchanged.
- Drafts remain non-runnable until approved and explicitly published. Exact inner DSL item semantics and historical backfill remain unresolved; no existing version title/review state is inferred.

## M06 — schedules and suite execution

- Runtime candidates now create/list suites and plans, read ordered suite-case associations, create/list/update/delete schedules, expose enable/disable and pause/resume aliases, and write idempotent trigger requests into an Outbox. Candidate migrations 009–010 are unapplied. Five-field cron validation, timezone/DST-aware `next_fire_at` calculation, 15-second Beat scanning, 60-second lateness policy, and schedule-event publishing are implemented. The schedule-event consumer creates an idempotent queued Run, pins the environment snapshot and published case versions, expands the accepted browser matrix into RunCases, and emits a `RUN_REQUESTED` Outbox event. This is only Run creation; M09 execution, Run APIs/events/SSE, and Browser Worker are unfinished.
- Schedule PATCH now accepts an optional reason, requires a non-empty reason when `enabled` actually changes, and writes the same `schedule_state_events` audit record as pause/enable. Cron/timezone edits recalculate `next_fire_at`; the Planning UI now exposes those edits. This candidate rule follows the pre-existing explicit state-change operations and remains pending HTTP/UI validation.
- Owner decisions (2026-10-27): use standard five-field Cron (minute, hour, day, month, weekday); skip nonexistent local times during a DST gap; run an ambiguous repeated local time once; when Beat resumes, skip missed instants and schedule the next future time, with a 60-second late window. These rules are implemented but remain unverified until the unified validation pass.
- The source uses pause/resume while candidate schema uses `enabled`; runtime keeps both aliases over the same schedule state. Trigger key scope/retention and schedule edit/delete races remain open. The owner-approved plan policy is `concurrency_mode=serial`, `max_concurrent_runs=1` by default, with bounded concurrency accepted when configured. The API validates and persists this policy, the UI shows it, and schedule-created Runs copy it. `RunAdmissionRepository.claim` now provides transaction-level slot admission by locking the plan and leaving over-limit Runs queued. It is not yet wired to a `RUN_REQUESTED` consumer because the Run execution Worker is still absent; until that integration exists, the limit is not an active execution guarantee. DST, Cron, missed-fire, and 60-second late-window rules are implemented pending unified validation.
- Source reconciliation confirmed the V10.3 trigger request requires `request_intent`, permits optional `reason`, and returns `Schedule`. The runtime now accepts/persists `reason` and returns the Schedule representation while retaining trigger status/source/error only in its internal persistence. This DTO alignment still needs HTTP contract validation.
- Owner accepted schedule Run browser-matrix source as `test_plans.policy.browser_matrix`, default `['chromium']`; only active cases with a published version are included, and each selected browser gets a RunCase.
- Owner accepted migration 010 candidate to add `run_cases.browser_name`, replace the two-column uniqueness with `(run_id, case_version_id, browser_name)`, and add `test_runs.environment_snapshot_id`. Migration 010 is unapplied and unvalidated; legacy RunCase rows remain NULL because historical browser identity is unknown.
